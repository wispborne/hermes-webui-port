## Context

- `mobile/android/` is generated by `expo prebuild` and not committed. Native settings come from `app.json` and config plugins.
- `mobile/app.json` sets the app ID `com.wispborne.hermes` and the version `0.1.0`. The app on the owner's phone is a development build with that ID, signed with the debug key.
- `.github/workflows/tag-release.yml` makes the web UI's `ui-*` tags on Gitea and skips on GitHub (`if: github.server_url != 'https://github.com'`). It ignores `mobile/**`. Gitea is where releases come from. GitHub only mirrors main.
- `.github/workflows/mobile.yml` type-checks and tests the app on `ubuntu-latest`. The Gitea runner uses the same label.
- The app accepts `http://` gateway addresses. Android blocks plain `http` in release builds unless the app allows it. Expo's debug builds allow it, which is why it works today.
- Obtainium can follow releases on a Gitea server. It can filter releases by title and pick an APK by file name.

## Goals / Non-Goals

**Goals:**
- Bumping the version in `mobile/app.json` on main is the only step needed to make a release.
- Every release APK is signed with the same key, so Obtainium can install it over the last one.
- The development build and the release app can be installed side by side.

**Non-Goals:**
- Google Play, F-Droid, or releases on GitHub.
- Over-the-air JavaScript updates (EAS Update).
- iOS.
- Releasing from pull requests or other branches.

## Decisions

### Variants and app IDs

`mobile/app.config.ts` reads `app.json` and changes it by build variant. `APP_VARIANT=development` gives:
- app ID `com.wispborne.hermes.dev`
- name "Hermes Dev"
- scheme `hermes-dev`

Anything else is the release variant, with the values in `app.json`. The `android` npm script sets `APP_VARIANT=development`, so `npm run android` keeps making the development build. Saved data, notifications and the background service are per app ID, so the two apps never share or fight over them.

Alternative considered: giving the release the new ID and leaving the development build on `com.wispborne.hermes`. Rejected, because the release is the app that lasts. It should have the plain ID.

### Version number

The version stays in `mobile/app.json` (`expo.version`), in the form `major.minor.patch`. `app.config.ts` sets `android.versionCode` to `major * 10000 + minor * 100 + patch`, so 0.2.0 is 200. It throws if a part isn't a whole number from 0 to 99, so a bad version fails the build instead of making a number that goes backwards.

### Signing

A config plugin, `mobile/plugins/with-release-signing.js`, adds a `release` signing config to the generated `android/app/build.gradle`. It reads four Gradle properties:
- `hermesKeystore`
- `hermesKeystorePassword`
- `hermesKeyAlias`
- `hermesKeyPassword`

When they're missing, as on the owner's PC, the release build falls back to the debug key, as Expo's template does today. The workflow passes them with `-P`.

The key is made once by `mobile/scripts/release-key-wizard.sh`. It runs `keytool` to make a keystore with a 30-year validity and prints the keystore as base64. It then walks the owner through:
- adding four Gitea Actions secrets: `HERMES_KEYSTORE_BASE64`, `HERMES_KEYSTORE_PASSWORD`, `HERMES_KEY_ALIAS` and `HERMES_KEY_PASSWORD`
- saving the keystore file and both passwords in their password manager
- deleting the local copy

Alternative considered: re-signing the APK with `apksigner` after the build. Rejected because the build would make a debug-signed APK first, and a signing step outside Gradle is easy to skip by mistake when building by hand.

### `http://` gateways

`expo-build-properties` sets `android.usesCleartextTraffic: true`, so release builds reach `http://` gateways like development builds do. Tailscale encrypts the traffic between devices. Removing `http://` support would be a separate decision, made in the sign-in screen, not here.

### Which phones

The release APK is built for `arm64-v8a` only (`-PreactNativeArchitectures=arm64-v8a`). That covers every Android phone from the last several years. It makes the APK about a quarter of the size of an all-architectures build, and the build faster. The emulator keeps using the development build.

### The workflow

`.github/workflows/mobile-release.yml` runs on pushes to main that change `mobile/**`, and on `workflow_dispatch`. It skips on GitHub. A `concurrency` group stops two runs from releasing the same version.

1. Read `expo.version` from `mobile/app.json`. If the tag `mobile-v<version>` already exists, stop. This is how "the version changed" is decided, so a later commit without a bump releases nothing.
2. Set up Node 24, Java 17 (`actions/setup-java`) and the Android SDK (`android-actions/setup-android`). Install the root and mobile packages, as the Mobile workflow does.
3. Run the type check and tests. A release never ships code that fails them.
4. Decode the keystore from the secret into the runner's temp folder. Run `npx expo prebuild --platform android --clean`, then `./gradlew assembleRelease` with the signing properties and the architecture. Gradle caches are kept between runs with `actions/cache`.
5. Check the APK's signature with `apksigner verify --print-certs`. Fail if it's the debug key.
6. Write the release notes. They're the subjects of the commits that changed `mobile/` since the last `mobile-v` tag (`git log --format='- %s' <last>..HEAD -- mobile/`). The first release lists every commit that changed `mobile/`.
7. Tag the commit `mobile-v<version>` and push the tag. Create the Gitea release through the API with the workflow's token:
   - title "Hermes mobile <version>"
   - body: the notes
   - one asset, `hermes-<version>.apk`

If any step after the tag fails, the run deletes the tag again, so the next run can retry the same version.

### Obtainium

The README gets an "Install with Obtainium" section:
- Add the Gitea repository URL as the app source.
- Set "Filter release titles by regular expression" to `^Hermes mobile`, so the web UI's `ui-*` releases are skipped.
- Set the APK filter to `hermes-.*\.apk`.

### Mobile workflow

`mobile.yml`'s generated-files check also compares `mobile/src/theme/themes.generated.json`. It was left out when that file was added.

## Risks / Trade-offs

- [The signing key is lost] → No later release can update the installed app. The owner would have to uninstall it, losing what it saved on the phone, and every release from then on uses a new key. The wizard makes the password-manager backup a step, not a suggestion.
- [The Gitea runner lacks the disk or memory for an Android build] → The first run shows it. The fallback is a script on the owner's PC that builds with the same Gradle properties and uploads to the release through the same API. That would be a follow-up change.
- [Moving the development build to a new ID] → The first release can't install over the current development build, because their signatures differ. The owner uninstalls it once. Sign-in, sessions and transcripts come back from the gateway. Appearance choices and unsent Outbox messages are lost.
- [`expo prebuild --clean` on the runner differs from the owner's PC] → Both come from the same `app.config.ts`, plugins and lockfile. The release build is also checked by the owner on their phone before this change is done.
- [A version bump and other changes land in one push] → That's fine. The release is built from that commit.
